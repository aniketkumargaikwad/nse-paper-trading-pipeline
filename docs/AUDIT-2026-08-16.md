## 1. Executive summary

You have a **correct, narrow backtester** with unusually honest reporting. It
is not yet a research platform.

The engineering that exists is sound: fills are conservative, look-ahead bias
has been actively hunted, and the system consistently refuses to report a
number it cannot justify. That is rarer and more valuable than it sounds.

But the product you described needs five things this cannot do:

| | |
|---|---|
| One strategy × many timeframes in a run | **Impossible today.** `Strategy.timeframe` is a single string |
| Custom groups ("My Banking Stocks") | Database supports it; **no way to create one** |
| Strategy versioning | **Does not exist.** Saving overwrites; old results point at a definition that no longer exists |
| Comparing runs | **Does not exist** |
| Expressing anything beyond indicator-vs-threshold | **The DSL cannot represent your two example strategies at all** |

The most serious issue is not a missing feature. It is that **a saved backtest
result is not reproducible**, because the strategy it refers to can be silently
rewritten. That undermines the entire research loop.

**One thing to stop believing immediately:** the System page's "Data provider"
is a dead readout (§4). And your one strategy's result is trustworthy in its
conclusion (no edge) but not reproducible as a record.

## 3. What is broken

**1. "Data provider: unknown" is a dead readout.** `app_pages/system.py:30-41`
reads `run_audit.details['provider']`. Nothing anywhere writes that key —
`backtest.py:774` writes `combinations`, `strategies`, `passed_kill_rules`,

Your actual provider is **Dhan**, set by `DATA_PROVIDER` in `.env`.

**2. `nse_holidays.yaml` covers only 2026.** 15 dates, no other year. The
backtester does not consult it (it works from candles that exist, so holidays
are handled implicitly — this is fine). The **paper engine does**
(`market_calendar.session_gate`), so from 1 January 2027 it will treat every
NSE holiday as a trading day.

**3. Taxes are not modelled.** `DEFAULT_COST_PER_TRADE_INR = 30.0` is described

0.025% on the sell side alone — on a ₹100,000 notional that is ₹25 on one leg,
before brokerage, exchange charges, GST and stamp duty. A flat ₹30 is
plausible for one trade size and wrong at others, and **it scales with notional
in reality but not in the model**.

**4. `data_quality_flags` has 0 rows** after backfilling 3.1M candles across 50
symbols. Either the checks never run during backfill, or they ran and found
nothing. **UNKNOWN — requires verification** by tracing whether
`candle_store.ensure_coverage` invokes `data_quality` on write.

**5. Paper trading has never run.** `trades` = 0, `positions` = 0. The code
looks complete and is tested, but has no production evidence.

## 7. Multi-timeframe — NOT supported

`Strategy.timeframe` is a single `str` (`strategy/parse.py:183`). One strategy
= one timeframe. `run_backtest` loops symbols, never timeframes.

To test 5m/15m/30m/60m today you must create **four separate strategies** with
four names, and there is no way to aggregate them.

**Minimum change:** make the run configuration, not the strategy, own the
timeframe list. The strategy should describe *rules*; the run should describe
*what to test them against*. Concretely:

```
BacktestConfig(strategy_version, universe, timeframes[], date_range, costs)
   → for each timeframe: for each symbol: simulate
   → results keyed by (timeframe, symbol) + per-timeframe aggregate
```

This is a schema change (`backtest_runs` gains `timeframe` per row, plus a
parent config row), an engine loop change, and a UI change. It does **not**
require touching the parser beyond making `timeframe` optional on the strategy.

## 9. Universes and survivorship

**Predefined:** NIFTY50, NIFTY100, NIFTY500 (650 members stored). BANKNIFTY,
SENSEX and sector indices are **not** configured — adding them is a few lines
in `NSE_INDEX_URLS` plus a refresh, assuming NSE publishes the same CSV shape.

**Custom groups:** the schema supports them (`symbol_groups.is_system=false`,
`source='custom'`) but **nothing can create one**. No UI, no CLI. This is the
smallest high-value gap in the system.

### Survivorship bias — answered explicitly

**Yes, the system has it, and it is documented rather than hidden.**

Backtesting NIFTY50 over 2 years tests **today's** 50 constituents across the
whole period. Stocks that were dropped are absent; stocks added after rising
are present for periods when they were not members. Results are flattered.

What exists: every run records `constituents_as_of` (2026-08-11 for yours), so
you always know how old the membership was. What does **not** exist:
point-in-time membership. `symbol_group_members` has no validity dates.

Free point-in-time constituent data for NSE is not readily available. The
honest options are (a) keep recording the caveat, (b) buy historical
constituent data, or (c) snapshot membership monthly from now on so that in
two years you have your own history. **(c) costs almost nothing and is worth
starting now** — the data you do not capture today is unrecoverable later.

## 11. DSL limitations — your two examples

I will not force these into the current schema.

### The A/B/C mathematical strategy

```
Level = (B × C) / A
```

**NOT SUPPORTED, and not close.** Three separate reasons:

1. **No arithmetic.** A condition compares an operand to a constant or another
   operand. There is no expression grammar — no `×`, `/`, `+`.
2. **No swing-point detection.** A, B, C are structural features of price, not
   indicator values. Nothing identifies a swing high/low.
3. **No variables.** Nothing can be named, stored, and referenced later.

### The Gold liquidity strategy

**NOT SUPPORTED.** Requires, none of which exist:

| Needed | Present? |
|---|---|
| Previous-day high/low | ❌ no previous-period references |
| Liquidity sweep detection | ❌ no event concept |
| "Fresh bearish confirmation candle" | ❌ no candle-pattern vocabulary |
| Entry on break of *that specific candle's* low | ❌ no reference to a remembered bar |
| Stop above *that* candle | ❌ stops are % or ATR from entry only |
| Swing-based target | ❌ no swing detection |
| Partial exit + runner | ❌ position is all-or-nothing |
| Max attempts per day | 🟡 `max_cycles_per_day` is close |
| Multi-timeframe (1m confirm) | ❌ single timeframe |

### Is the DSL fundamentally too restrictive?

**Yes — for the product you described.** It is well-built for what it models:
stateless, single-timeframe, indicator-threshold strategies. It cannot express
**state**, and most real discretionary strategies are state machines: *wait for
X → then watch for Y → then enter → then manage*.

That is a modelling gap, not a bug. No amount of adding fields fixes it; the
execution model itself assumes "evaluate a boolean per candle".

## 12. Recommended strategy representation

Your instinct is **correct**:

```
Natural language → AI → canonical IR → validation → engine
```

Generating Python or Pine Script directly would be worse, for reasons that
matter here specifically:

- **Unvalidatable.** You cannot prove generated Python is free of look-ahead
  bias. A constrained IR can make it *unrepresentable*.
- **Unsafe.** Executing AI-generated Python against your database is arbitrary
  code execution.
- **Undiffable.** You cannot meaningfully compare strategy v1 and v2.
- **Pine Script** is not an option — it is TradingView's proprietary runtime.

### The shape I would recommend

Keep YAML as the surface (readable, pasteable, AI-friendly) but change the
**execution model** from *boolean-per-candle* to a **state machine with an
expression language**.

```yaml
version: 3
states:
  - name: waiting_for_sweep
    on:
      - when: "low < prev_day.low"          # expression, not a comparison node
        set: {swept_at: "bar.index"}
        goto: waiting_for_confirmation

  - name: waiting_for_confirmation
    timeout: {bars: 20, goto: waiting_for_sweep}
    on:
      - when: "candle.is_bearish and close > prev_day.low"
        set: {confirm_high: "high", confirm_low: "low"}
        goto: armed

  - name: armed
    on:
      - when: "low < confirm_low"
        enter: {side: short, stop: "confirm_high", target: "swing.low(20)"}
        goto: in_position
```

Three additions carry almost all the missing capability:

1. **An expression language** — arithmetic, comparisons, boolean logic over a
   defined namespace (`close`, `prev_day.high`, `swing.low(n)`, `atr(14)`,
   user variables). Parsed to an AST you control, evaluated with no `eval`.
2. **Named variables with assignment** — this is what `(B × C) / A` needs.
3. **States with transitions** — this is what every "wait for, then" strategy
   needs.

Then layer on: multi-timeframe references (`daily.close`, `m1.low`), partial
exits, and a management block.

**This is a v3, not a patch of v2.** v2 strategies would migrate cleanly (a
one-state machine), which is why the existing migration infrastructure is worth
having.

## 14. Intracandle execution — current behaviour

Your exact example (`open 100, high 110, low 90, close 105, stop 95,
target 108`):

**The engine assumes the STOP hit first.** Order in `backtest.py`:

1. Signal exit (queued from previous close) — fills at open
2. **Stop loss** (including trailing)
3. Target
4. Square-off

For your candle: low 90 ≤ stop 95 → **exit at 95, reason `stop_loss`**. The
target is never considered even though 110 ≥ 108.

**Gaps:** if the open is already past a level, the fill is at the **open**, not
the level. Your example with `open 94` would fill at 94, not 95 — a worse
price, correctly modelled.

**Same-candle entry and exit:** impossible. Entry fills at a candle's open;
exits are checked on that same candle onward, so the minimum hold is one bar.

**Verdict: conservative.** This is the correct bias for research. It will
understate a strategy that genuinely hits targets before stops, which is the
right direction to be wrong in.

## 15. Metrics — current vs recommended

factor, max drawdown %, longest losing streak, Sharpe (daily), Sortino (daily),

That is a solid core. Notably it reports **null, not zero**, when a metric is

**Minimum additions for a serious platform**, in priority order:

| Metric | Why | Effort |
|---|---|---|
| Equity curve series | Everything visual depends on it | Low — the data exists |
| Per-symbol Sharpe/CAGR/expectancy | Ranking needs it | Low — call existing function per symbol |
| Average win / average loss / payoff ratio | Expectancy without these is opaque | Low |
| Largest win / largest loss | Outlier dependence | Low |
| Average holding time | Reveals whether it is the strategy you think | Low |
| Exposure % | A strategy in the market 3% of the time is not comparable to one at 80% | Medium |
| Monthly/yearly return table | Regime dependence, consistency | Medium |
| Rolling Sharpe / rolling drawdown | Stability | Medium |
| Consecutive wins/losses | Psychological and sizing reality | Low |
| Calmar | Return per unit of worst pain | Low |

**Skip for now:** VaR/CVaR, Omega, market participation. They are not
informative at your stage and add interpretation burden.

### `Object of type bool_ is not JSON serializable`

**Source:** `metrics.evaluate_kill_rules` produces flags like
`"passed": metrics.net_pnl > 0`. Prices come from numpy arrays, so `net_pnl` is
`numpy.float64` and the comparison yields `numpy.bool_`, which the JSON encoder
rejects when writing the `jsonb` column.

**When:** any database-backed backtest. It never appeared before because every
earlier run used `--no-db`.

**Could it corrupt results?** No — it failed *before* writing. Nothing partial
was stored. It **lost** results (all 50 per-symbol rows, since that insert runs
first) but never corrupted them.

**Affects paper trading?** Same latent risk existed on any numpy-derived value.

**Fix:** applied today (`445bd94`) — `db.to_native()` converts at the database
boundary, with two regression tests.

- `DNS_PROBE_FINISHED_NXDOMAIN` — your ISP's DNS, not the app (verified: the
  server returns HTTP 200)

# What I should do next as the owner

Written plainly.

### 1. What you currently have

A **correct backtester for simple indicator strategies**, with genuinely
careful data underneath and reporting that refuses to flatter you. 3.1M
candles, 50 stocks, 2 years. It works, and today it correctly told you your one
strategy is bad.

### 2. What you should NOT trust yet

- **Any saved result as a permanent record.** Editing a strategy overwrites it;
  the old result then describes something that no longer exists.
- **The System page's "Data provider".** It always says unknown. You are on
  Dhan.
- **P&L to the rupee.** Costs are a flat ₹30 estimate, not real Indian taxes.
- **Any universe result as unbiased.** You are testing today's NIFTY50 over the
  past — flattering by construction.
- **That paper trading works.** The code is tested but has never run for real.

### 3. How to use it safely right now

Test simple indicator ideas on NIFTY50 at 60m. Read **"symbols profitable"
before net P&L** — it is the honest number. Treat anything that passes as
*interesting*, never as *proven*. Do not deploy to paper trading until you have
watched one run succeed.

### 4. What is missing

Multi-timeframe. Custom groups. Strategy versions. Result comparison. And a
strategy language that can express the kinds of strategies you actually want to
test — which is the deepest gap, and the one no amount of UI fixes.

### 5. What to build next, and why in this order

**First: strategy versioning.** Not exciting, but it is the foundation. Until a
strategy definition is immutable once tested, every result you accumulate is
provisional and every comparison you make is unsound. Everything else is worth
less without it.

**Second: multi-timeframe runs.** The single capability you named most
explicitly, and the current limitation forces you to duplicate strategies.

**Third: custom groups.** Hours of work; the database is already ready.

**Fourth: the v3 strategy language.** The largest piece, and the one that turns
this from a backtester into the platform you described. Do it after the
foundations, because it is much harder to version and compare strategies you
cannot yet represent.

### 6. Why that order matters

You are trying to find a winning strategy. Every item above is ranked by how
much it protects you from **believing a wrong answer** — not by how impressive
it looks. Versioning first because irreproducible research is not research.
Timeframes next because it is your stated need. The language last because it is
the biggest, and building it on unversioned, uncomparable foundations would
mean building it twice.
