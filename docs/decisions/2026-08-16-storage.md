# Storage decision — CockroachDB, or something else?

**Question:** storage is near the Supabase free-tier limit. Should we migrate to
CockroachDB?

**Answer: no — it solves the wrong problem.** Split the candle store out
instead. Evidence below.

---

## What is actually consuming the space

Measured against the live database, 16 Aug 2026:

| Table | Rows |
|---|---|
| `candles` | 3,119,362 |
| everything else combined | 5,961 |

**Candles are 99.8% of all rows.** ~357 MB of the ~500 MB free tier.

The application data — strategies, results, universes, instruments, audit — is
**six thousand rows**. That will never trouble a free tier. There is no
database-sizing problem here; there is one enormous table with a very
particular shape sitting in a database that was not designed for it.

Candles are: append-only, immutable once written, never updated, never joined
transactionally, always read as a contiguous time range for one symbol.

That is an analytical workload, not a transactional one.

---

## Measured alternative

RELIANCE, 2 years of 5-minute candles (37,021 rows), same data both ways:

| | Supabase (PostgREST, paged) | Parquet + zstd |
|---|---|---|
| Bytes per candle | ~120 | **21.5** |
| Read time | **10.2 s** | **224 ms** |
| 50 symbols | ~357 MB | **~38 MB** |

**5.6× smaller. 46× faster.**

The speed number matters as much as the size. It is why a 50-symbol backtest
takes minutes today: PostgREST returns 1,000 rows per HTTP request, so 1.85M
rows is roughly 1,850 round trips.

---

## Why CockroachDB does not fix this

CockroachDB Serverless offers roughly 5 GB free versus Supabase's 500 MB —
about 10× more room. Tempting, but:

**1. It keeps the same shape.** 3.1M rows stay 3.1M rows at roughly the same
size each. You buy headroom, not efficiency.

**2. It does not fix the read speed.** Distributed SQL has *higher* per-query
latency than single-node Postgres, not lower. The slow part of a backtest
would stay slow, and could get slower.

**3. It does not survive the real target.** NIFTY500 × 5 years × 5-minute is
~47M candles. At ~120 bytes that is **~5.4 GB — over CockroachDB's free tier
too.** The same conversation would recur in a few months. As Parquet it is
~1.0 GB.

**4. It costs a large rewrite.** Supabase is not just Postgres; the codebase
uses PostgREST's client throughout — **50 call sites** across `db.py`,
`supabase_candle_backend.py` and `app_common.py`, all shaped like
`.table(x).select().eq().execute()`. CockroachDB speaks the Postgres wire
protocol, not PostgREST. Every one of those becomes raw SQL via psycopg or
SQLAlchemy. Row Level Security policies would need rebuilding. Anything later
relying on Supabase auth would need replacing.

That is a substantial migration whose payoff is 10× headroom on a table that
should not be there at all.

---

## Recommended: split the two workloads

```
Application data  (~6,000 rows)         →  stays in Supabase
  strategies, versions, results,           free forever at this size
  universes, instruments, audit            keeps PostgREST + RLS
                                           zero rewrite

Candle store      (3.1M+ rows)          →  Parquet, one file per
  OHLCV                                    (symbol, timeframe, year)
                                           read with DuckDB or pandas
```

**Phase 0 anticipated exactly this.** Its design doc evaluated three storage
approaches, chose row-per-candle deliberately for simplicity, and put the store
behind a narrow interface *specifically* so a swap would be contained:

> "with the store behind a narrow repository interface so B or C remains a
> **contained, single-module swap** rather than a redesign."
> — `docs/superpowers/specs/2026-08-08-data-foundation-design.md` §2.3

That interface is `CandleBackend` in `candle_store.py:43` — six methods.
Nothing above it knows or cares where candles live. This migration means
writing a second implementation of six methods, not touching 50 call sites.

The Phase 0 estimate for approach C was 150–190 MB for Nifty100 × 5 years. The
measurement above (21.5 bytes/candle) puts it at ~200 MB. The estimate held.

---

## The complication that must be solved first

**Parquet files need somewhere to live, and Railway's filesystem is
ephemeral.** Containers get a fresh disk on every deploy, so files written
locally vanish. This is the one genuine obstacle.

Options, cheapest first:

| Where | Free tier | Notes |
|---|---|---|
| **Cloudflare R2** | 10 GB + no egress fees | S3-compatible; DuckDB reads it directly. Strongest option |
| Supabase Storage | 1 GB | Already have the account; enough for NIFTY100, not NIFTY500 |
| Backblaze B2 | 10 GB | S3-compatible; egress charged beyond a threshold |
| Railway volume | paid | Persistent disk attached to the service |

**Recommendation: Cloudflare R2.** Ten gigabytes free comfortably holds
NIFTY500 × 5 years (~1 GB), it is S3-compatible so DuckDB can query it without
downloading whole files, and R2 famously does not charge egress — which matters
because a backtest reads a lot and writes little.

**UNKNOWN — requires verification:** current R2 free-tier terms and whether
DuckDB's httpfs extension performs acceptably against R2 from Railway's region.
Worth a small spike before committing.

---

## Honest costs of the recommended path

Not free of downsides:

- **Two storage systems** instead of one. More to reason about, more to break.
- **No SQL over candles.** Ad-hoc `select * from candles where...` in the
  Supabase UI stops working. DuckDB restores it, but it is a different tool.
- **Coverage tracking gets subtler.** `candle_coverage` currently lives beside
  the candles; it would stay in Supabase while the data moves, so the two can
  drift. Phase 0's rule — never claim coverage you do not have — needs
  re-establishing across the boundary.
- **A migration to write and verify.** 3.1M rows to export, and a proof that
  what comes back is byte-identical.

Against that: 5.6× smaller, 46× faster, headroom for the target universe, and
the seam already exists.

---

## When CockroachDB *would* be right

Not never — just not here:

- Multiple users writing concurrently from different regions
- A need for horizontal write scaling
- Strict geo-distribution or residency requirements

None apply to a single-operator research tool.

---

## Cheaper stopgaps, if this is not worth doing yet

The recommendation above is real work. Two smaller moves buy time:

1. **Supabase Pro, $25/month** — 8 GB. Buys perhaps a year and zero
   engineering. Does not fix the 46× read penalty.
2. **Store only what you test.** You have 2 years for 50 symbols. Dropping
   unused symbols or shortening history frees space immediately.

Neither addresses the underlying shape, but both are honest choices if
finding a strategy matters more right now than storage architecture.

---

## Recommendation

1. **Do not migrate to CockroachDB.** Wrong problem, large rewrite, and it
   still fails at the target scale.
2. **Do split the candle store to Parquet on R2**, behind the existing
   `CandleBackend` interface — but not before strategy versioning (P0 in the
   audit), because irreproducible research is a worse problem than slow reads.
3. **If space becomes urgent first**, take Supabase Pro as a stopgap; it is
   $25 against days of engineering.
